## Phase 2 — Map tab (`src/app/(tabs)/map.tsx`) ✅ (MVP)
- [x] Map: Home — [map.tsx](src/app/(tabs)/map.tsx) rebuilt: full-bleed `PlaceMap` + floating search/filter row on top + floating "add place" button bottom-right + the floating nav bar underneath it all.
- [x] Tap icon info card — marker tap opens [`PlaceInfoCard`](src/components/place-info-card.tsx) as a bottom sheet; rating/visited/reflection edits write straight through `usePlaces().updatePlace`, delete removes and closes the sheet.
- [x] Filter activation / Filtered map — filter button opens [`FilterPanel`](src/components/filter-panel.tsx); category + visit-status filters actually narrow which pins render.
- [x] Map after place added — confirmation state. Saving in the Phase 4 flow does `router.dismissTo({ pathname: '/', params: { focusPlaceId } })`; the map screen adjusts `selectedPlaceId` during render when a new `focusPlaceId` param arrives (comparing against the last one it's already handled, per [React's "storing info from previous renders" pattern](https://react.dev/reference/react/useState#storing-information-from-previous-renders) — not a setState-in-effect, which `eslint-config-expo`'s newer `react-hooks/set-state-in-effect` rule now flags), so the new pin's `PlaceInfoCard` pops open immediately as confirmation.

**Critical bug caught and fixed:** `expo-maps` throws `Error: Cannot find native module 'ExpoMaps'` at *import time* on web — confirmed by reading `expo-modules-core`'s actual source (`requireNativeModule.web.ts` throws when no web module is registered, which is the case here). The `Platform.OS === 'web'` guard I wrote inside `PlaceMap` back in Phase 0 never actually helped, because the crash happens before the component function even runs — it's a module-level `require('expo-maps')` side effect, not something a runtime `if` can catch. Real fix: split into [`place-map.tsx`](src/components/place-map.tsx) (native only) and [`place-map.web.tsx`](src/components/place-map.web.tsx) (the fallback, with zero `expo-maps` import), so Metro's platform resolution excludes `expo-maps` from the web bundle entirely. Verified this actually worked by checking the compiled web bundle no longer contains any `expo-maps` reference, and by fetching the server-rendered HTML for `/` and confirming the fallback text renders — not just that the bundle compiles, which was insufficient (that's how this bug slipped through undetected in Phase 0, when `PlaceMap` existed but nothing imported it yet).

**Location markers — filled/unfilled now works, on both platforms.** Apple Maps markers (`AppleMapsMarker`) turned out to only support SF Symbols, no custom bitmap — but `expo-maps` has a separate `AppleMapsAnnotation` type (via the `annotations` prop, not `markers`) that *does* take a custom `icon` image. Switched `PlaceMap` to use that on iOS, and `GoogleMapsMarker.icon` on Android — both now render real generated pin art: solid colored teardrop + white category glyph when visited, white/hollow teardrop + colored outline + colored glyph when not. Images are loaded via `expo-image`'s `useImage()` and passed as the native `icon`.

Getting real marker art required an actual image-rasterization step this environment didn't have (no ImageMagick, only Windows' unrelated built-in `convert.exe`). Installed `sharp` as a devDependency and wrote [scripts/generate-markers.js](scripts/generate-markers.js), which composites a hand-authored teardrop pin shape with each category's Figma icon (tinted white or category-color depending on state) into 8 PNGs under [assets/images/markers/](assets/images/markers/). Re-run `node scripts/generate-markers.js` any time the pin shape or category icons need regenerating. I looked at the actual output PNGs before wiring them in — they read clearly as filled vs. outline.
- **Filter Panel** — Figma's is a multi-level drill-down (Location, Category, Rating, Your Lists, Visit Status, each its own sub-screen). Built a single-level panel with just Category + Visit Status — Rating and Your Lists filters need features that don't exist yet (Lists is explicitly deferred; a rating filter is easy to add later if wanted).
- **Search bar** — wired to filter your own saved places by name/address, not a live external places search (that's the separate "Add a place" flow in Phase 4).
- **Edit button** — was a no-op when this phase shipped; fixed in Phase 5 with a dedicated edit screen. Delete is fully wired.

**Verification limits — please read:** `expo-maps` cannot run in Expo Go or in a browser at all — it needs a real dev-client build on an iOS or Android device/simulator. Everything above is `tsc`-clean, lint-clean, and I confirmed via server-rendered HTML that the whole screen (search bar, filter button, add button, nav bar) mounts and renders without crashing on web. But the actual map + pins + marker taps have **not been visually verified anywhere** — that only happens on a real native build, which this environment can't produce. First real device test is on you.

## Phase 4 — Add a Place flow ✅ (MVP)
- [x] Add a place — search bar + results — [`add-place.tsx`](src/app/add-place.tsx), a 2-step screen (`'search' | 'details'`) presented as a real modal route (see routing fix below). Typing debounces 500ms into [`searchPlaces()`](src/lib/place-search.ts).
- [x] Cafe result tapped — search result selected state — tapping a [`SearchResultRow`](src/components/search-result-row.tsx) seeds the details step from that result (name/address/lat-lng/category guess) and advances `step`.
- [x] Rating and reflecting place — details step reuses the same `CategoryTag` (now tappable, one per category, to fix a wrong guess) + `StarRating` + `VisitToggle` + `ReflectionEntry` + `SaveToMapButton` already built in Phase 1, so it's the same visual language as `PlaceInfoCard`. **Photo variant not built** — there's no image-picker dependency in the project yet (`expo-image-picker` isn't installed) and it wasn't part of what was asked; flagging so it's a conscious "not yet" rather than a silent gap. `Place.photoUri` already exists in the data model for whenever it's added.

**No place-search API was configured** (Phase 0's Google Maps key is for map tiles/markers, not search, and there's no Apple/Google Places key either). Used [Nominatim](https://nominatim.openstreetmap.org) (OpenStreetMap's free, no-API-key search) via plain `fetch` in [`place-search.ts`](src/lib/place-search.ts) — confirmed by hand that searching "Portland Art Museum" returns the real venue with a real address. Debounced 500ms, aborts stale in-flight requests, and sends a `User-Agent` per Nominatim's usage policy (browsers silently drop custom `User-Agent` headers on web, so that identification only actually reaches Nominatim on native — an unavoidable web platform restriction, not a bug). OSM's `class`/`type` tags are mapped onto this app's 4 categories with a best-effort heuristic (`inferCategory`) since they don't line up 1:1; shown as a preselected-but-changeable `CategoryTag` rather than something that has to be right. This is fine for a single personal user's request volume — revisit before any real scale-up (Nominatim's public instance isn't meant for heavy traffic).

**Routing bug found and fixed:** `router.push('/add-place')` from the map's add button was wired up in Phase 2, but couldn't have ever worked. The root [`_layout.tsx`](src/app/_layout.tsx) rendered `<AppTabs />` directly — and `AppTabs`'s `expo-router/ui` `Tabs` component builds its own navigator containing *only* the routes wired up as `<TabTrigger>`s (index/explore/profile). `add-place.tsx` existed as a file but wasn't part of any navigator the router could actually push onto. Fixed by moving index/explore/profile into a [`(tabs)`](<src/app/(tabs)/_layout.tsx>) route group (a group segment doesn't change any URL — confirmed the generated `.expo/types/router.d.ts` still resolves `/`, `/explore`, `/profile` unchanged) and giving the root layout a real `Stack` with `(tabs)` and `add-place` (`presentation: 'modal'`) as siblings. This is also the standard expo-router pattern for combining a custom tab bar with modal routes, confirmed against the current SDK 57 docs per `AGENTS.md`.

**Verified:** `tsc` and `eslint` clean (including a newer `react-hooks/set-state-in-effect` rule this Expo SDK bump apparently introduced — see the note on Phase 2's "confirmation state" item above for how that shaped the implementation). Confirmed via server-rendered HTML that `/`, `/explore`, and `/add-place` all return 200 and render real content (title text, search placeholder, the "Portland Art Museum" example copy) with no error-boundary output — not just that the bundle compiles. **Not yet checked:** the actual live Nominatim network call, the modal's native slide-up presentation, and the full tap-through flow on a real device/simulator — all need a real run, which this environment can't do for a native-only stack (same limitation noted in Phase 2).

## Follow-up fixes (post-Phase 4)
- **Tab route files renamed for consistency** — `(tabs)/index.tsx` → [`(tabs)/map.tsx`](<src/app/(tabs)/map.tsx>), `(tabs)/explore.tsx` → [`(tabs)/list.tsx`](<src/app/(tabs)/list.tsx>). The component names (`MapScreen`/`ListScreen`) and the nav bar's `accessibilityLabel`s already said "Map"/"List" — only the underlying file/route names and `app-tabs.tsx`'s `<TabTrigger name="index" href="/">`/`name="explore" href="/explore"` were stuck with old Expo-starter naming. Renamed both, updated `app-tabs.tsx`'s trigger names/hrefs to `map`/`/map` and `list`/`/list`, and `(tabs)/_layout.tsx`'s `initialRouteName` to `'map'`. The map tab's URL is `/map` now instead of `/` — a deliberate side effect, not an accident: a route group's `index.tsx` is special-cased to the group's own bare path, so keeping the file named `index.tsx` while everything else used feature names wasn't an option without renaming. Updated the one other hardcoded reference — [`add-place.tsx`](src/app/add-place.tsx)'s `router.dismissTo({ pathname: '/map', ... })`. Verified via the regenerated `.expo/types/router.d.ts` (now exactly `/map` | `/list` | `/profile` | `/add-place`, no stale `/` or `/explore`) and via server-rendered HTML that all four new routes return 200 with real content while the old `/` and `/explore` correctly 404 now. **Correction, found later:** that `/` 404 was checked as a pass here, but it's actually a bug — see "First real native build" below for why and the fix (`src/app/index.tsx` now redirects `/` → `/map`).
- **`npm audit` pass** — fixed what could be fixed without a breaking downgrade: `npm audit fix` (no `--force`) bumped `browserslist` and a cluster of `expo-*`/`@expo/cli` packages to newer patch releases already inside their declared `~57.0.x` ranges in `package.json` (no `package.json` edits needed — just a stale lockfile catching up to already-permitted versions), clearing the `@expo/cli` moderate advisory and the `browserslist` high one (20 → 19 vulnerabilities). **Caught a real regression this introduced:** that first `npm audit fix` left `node_modules` in a broken state on Windows — a dangling `readlink` on `babel-preset-expo`'s nested `@react-native/babel-plugin-codegen`, crashing Metro with `EINVAL` and 500-ing every route. A clean `rm -rf node_modules && npm install` from the updated lockfile fixed it; re-verified the dev server actually boots and every route still renders before calling it done.

**Follow-up: patched `uuid` directly via `package.json` `overrides`** (19 → 7 vulnerabilities) instead of accepting npm's forced downgrade. `uuid` was vulnerable at `<11.1.1` via two paths — `@expo/ngrok` and `xcode` (→ `@expo/config-plugins` → `expo`/`expo-splash-screen`) — and npm's own forced fix wanted to downgrade `expo`/`expo-splash-screen` to ancient pre-SDK-57 versions to "solve" it. Checked both actual call sites first (`@expo/ngrok/index.js` and `xcode/lib/pbxProject.js`) — both just call the stable `uuid.v4()`, unchanged across major versions — so overriding straight to the patched `11.1.1` (pinned via `"overrides": { "uuid": "11.1.1" }`, no `expo`/`expo-router`/`expo-splash-screen` version changes at all) was safe. Verified: `npm ls uuid` shows one deduped copy at `11.1.1` everywhere, `tsc`/`eslint` clean, and confirmed via a real dev-server boot that `/map`, `/list`, `/profile`, `/add-place`, `/edit-place` all still return 200.

**Confirmed `decode-uri-component` and `image-size` are genuinely unsafe to patch, not just npm-semver-blocked** — actually tested each patched version in isolation rather than taking npm's word for it: `image-size@2.0.2`'s CJS `require()` no longer returns a directly-callable function (only `.default` does), and Metro's own `Assets.js` calls `_imageSize.default(isImageInput)` with a raw file path string in the common case — but `image-size@2.x` now throws on anything that isn't a `Buffer`/`ArrayBufferView`, so upgrading would crash asset bundling for every image in the app, not just fail an advisory check. Same story for `decode-uri-component@0.5.0`: it changed from a plain callable export to `{ __esModule: true, default: fn }`, but `query-string/index.js` (used by `expo-router`) does `decodeComponent(value)` — calling the required module directly — so that upgrade would throw `TypeError: decodeComponent is not a function` on every route param parse. Both remain on their vulnerable versions deliberately; both sit in dev-toolchain/build-time-only code paths (Metro's asset transformer; `expo-router`'s dev-time URL parsing) rather than code reachable by untrusted end-user input, so the residual risk is low. Re-check on the next Expo SDK bump — a `metro`/`expo-router` update may ship a version that's compatible with the newer, patched releases.
